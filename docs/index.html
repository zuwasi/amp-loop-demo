The idea
"I don't prompt Claude anymore. I have loops running that prompt it and figure out what to do. My job is to write loops."
— Boris Cherny, lead of Claude Code @ Anthropic
Two mental models

The shift in one picture

Today: you prompt

Human types prompt → AI replies → human reads → human types next prompt. You are the loop.

Better: you build the loop

You design the system that decides what to ask. The AI iterates until the goal is met.

You move up one level of abstraction.

What a loop looks like

The shape

Human writes loop ──▶ Loop prompts agent ──▶ Agent acts & replies ▲ │ └────────── Loop decides next step ◀─────────┘

Three jobs the loop owns: keep context, decide "done", write the next prompt.

Why Amp makes this stronger

Loop an agent, not a chatbot

  • A raw model only emits text — your loop must bolt on tools.
  • Amp is already an agent: terminal, file editing, search, skills.
  • So each loop step can actually change the repo and verify itself.
The three building blocks

Amp CLI primitives

amp threads new                          # a thread = the loop's memory
amp threads continue <id> -x "<prompt>"  # one step, keeps context
amp -x "<prompt>"                        # one-shot, no memory
amp -x "<prompt>" --stream-json | jq ... # structured output to parse

--dangerously-allow-all lets it run unattended. Use only on trusted work.

The minimal loop

~15 lines of PowerShell

$tid = (amp threads new).Trim()
$prompt = $task
for ($i=0; $i -lt 10; $i++) {
    $reply = amp threads continue $tid -x $prompt --dangerously-allow-all
    if ($reply -match "TASK_COMPLETE") { break }   # LOOP decides done
    $prompt = "Review vs the goal; if finished reply TASK_COMPLETE,
               else do the next step."             # LOOP writes next prompt
}
The golden rule

A loop is only as good as its "done" gate

Weak gate

"Does this look right?" — the AI judges itself. Unreliable, not auditable.

Strong gate

A deterministic check: a test, a build, a parser, a linter that returns pass/fail.

Pattern: deterministic verifier = gate, Amp = fixer.

The classic loop

Make the tests pass

run test suite ──pass──▶ STOP ▲ │ │ failures + output │ └──── Amp fixes ◀─────┘
  • Gate = your existing test command (exit code 0 / non-zero).
  • Each pass, feed the failures to Amp; it edits code and re-runs.
  • Same shape works for: lint clean, build green, type errors → 0.
More places it fits

Where teams use loops

  • Migrations — upgrade an API across N files until build is green.
  • Flaky-test triage — re-run, isolate, fix, confirm stable.
  • Coverage / lint debt — drive a metric to a target threshold.
  • Doc & config consistency — check a rule, fix, re-check.
  • Codegen + verify — generate, compile, correct, repeat.
Pick the right work

When loops win — and when they don't

Great fit

Objective, repeatable goals: tests passing, build green, coverage, lint, migrations, refactors.

Poor fit

Open judgment & design: product decisions, architecture trade-offs, naming. Keep these human-driven.

Do it safely

Guardrails

  • Run on a git branch, never main.
  • Always set MaxSteps — bound the blast radius.
  • Narrow the prompt: "fix only X, change nothing else."
  • Keep a human approval gate before merge.
  • Drop --dangerously-allow-all until you trust that loop.
Real incident · matmul benchmark

When "one-shot" looked as good as the loop

We benchmarked an agent optimizing a C++ matmul. Running the one-shot (no external loop) repeatedly with Claude:

run 1 (one-shot):  226 GFLOP/s   correct
run 2 (one-shot):  277 GFLOP/s   correct   "...the sweet spot my
                                            project memory records"

The one-shot kept getting better each run and nearly matched the loop. Suspicious — a true one-shot has no reason to improve.

Root cause

There were two hidden loops

1 · Across runs (memory) — Claude: YES · Amp: NO

Claude auto-wrote project memory each run (optimal kernel, traps, regressions) and replayed it — 12 sessions, 4 memory files. Amp's -x starts a fresh thread every run and writes no learned memory, so it stays cold. This is the loop that broke the benchmark — Claude-specific here.

2 · Inside one run (tools) — both agents

Even a cold run self-iterates: build, see correct=0 (FMA bug), fix it — all in one call. Inherent to any tool-using agent. Benign: it doesn't compound across runs, and reset doesn't touch it.

So a repeated "one-shot" silently improves on Claude, but not on Amp.

Lessons for fair benchmarks

What reset does — and doesn't — fix

  • Amp -x needs no reset — fresh thread per run, already cold.
  • Claude needs its project memory cleared for a fair cold one-shot.
  • Reset stops loop #1 (cross-run learning) but NOT loop #2 (in-call self-iteration).
  • Reset can't erase what the model already knows (matmul is textbook).
  • To prove loop > one-shot: control memory and pick a task the model can't recall.

Not "Amp wins": Claude's memory is a feature (it learns) — just a confound when benchmarking.

Takeaway

Stop being
the loop.
